# 끊김 없는 저장 0.13.0 — E2E 후보 확인

[문서 목록](README.md) · [저장 구조](cooperative-save.md)

이 문서는 실제 게임에서 아직 검증하지 않은 결과를 확인하는 절차입니다.
합성 JVM 테스트 통과가 드래그·프레임 시간·차량 복원 검증을 대신하지는 않습니다.
이 후보는 저중단 저장이며 모든 직렬화가 논블로킹이거나 월드 전체가 원자적 스냅샷이라는 보장은 없습니다.

## 실행 준비

- API 8 이하에서 처음 전환할 때는 앱과 게임을 완전히 종료한 뒤 후보 폴더의 `PzTools.App.exe`를 실행합니다.
  앱·작업 프로그램·JAR을 일부만 교체하지 않습니다. Bootstrap API 9 / 모듈 0.13.0입니다.
- Windows x64와 .NET 10 x64 런타임이 필요합니다. 서명되지 않은 테스트용 빌드입니다.
- 반드시 버려도 되는 새 테스트 월드를 사용합니다. 중요한 원본 월드로 실패·강제 종료 검사를 하지 않습니다.
- 백업 위치는 **새 테스트 전용 폴더**로 설정합니다. 기존 백업 위치를 유지한 채 세이브 루트만
  축소하면 기존 고아 백업 정리 정책에 영향을 줄 수 있으므로 그렇게 설정하지 않습니다.
- 첫 비교는 자동 백업을 끄고 수동 백업으로 수행합니다. 기존 설정은 이 빌드에서도 유지되므로
  확장 토글과 백업 위치를 직접 확인합니다. `백업 전 게임 저장`은 켜둡니다.

## 기본 저장과 비교

같은 월드·장소·모드 조합에서 확장을 끈 저장과 켠 저장을 각각 반복합니다.
첫 연결/클래스 준비 시간을 일상적인 저장 시간과 혼동하지 않습니다.
확장을 켠 경우 카드가 실제로 확장 저장 완료를 보고했는지 확인합니다.
`기본 저장 사용`과 사유 코드가 표시되었다면 확장 성능을 검사한 것이 아닙니다.

| 확인 | 기대 동작 |
| --- | --- |
| 아이템을 계속 끌고 있는 중 저장 요청 | 드래그 종료를 기다리지 않고 저장이 실행되어야 합니다. 저장 때문에 드래그·아이템·포커스가 바뀌면 실패입니다. |
| 버튼 해제 직후, UI의 드롭 처리 전 저장 | 저장이 별도 UI 갱신을 끼워 넣지 않아야 합니다. 이후 정상 입력 처리에서 드롭이 한 번만 완료되어야 합니다. |
| 텍스트 선택·모달 조작·일반 버튼 유지 | 특정 UI 상태 때문에 저장을 보류하지 않습니다. 정상 조작·취소를 되돌리거나 끝난 드래그를 복구하면 안 됩니다. |
| 일반 게임 저장·다른 모드의 저장 | 원래 진입점과 미리보기 동작을 유지합니다. 동일 데이터의 의존 잠금 대기는 가능하며 무간섭을 보장하지 않습니다. |

드래그 검사는 게임 포커스를 유지한 상태에서 정기 백업이 실행되도록 합니다. 앱으로 전환해
수동 백업을 누르면 포커스 변경 자체가 조작에 영향을 줄 수 있습니다. 저장 완료 전에 드래그를
풀지 않아도 요청이 진행되는지 확인합니다. 일시정지·저장 작업 준비 조건은 별개로 유지됩니다.

## 보존·취소·복귀 확인

발견만 하고 타지 않은 차량, 컨테이너에서 옮긴 아이템, 모드의 저장 데이터를 기록한 뒤
초기 백업과 다음 증분 백업을 각각 **별도 복원 위치**에 복원하여 게임에서 확인합니다.
세이브 폴더에 파일이 생겼다는 사실만으로 데이터 보존을 판정하지 않습니다.

정기 백업은 일시정지 중 대기하고, 사망 백업은 같은 캐릭터의 실제 JVM 사망 사건을 사용해야 합니다.
저장 시작 전 취소는 쓰기를 시작하지 않아야 하며, 시작 후 취소는 완료 불명일 수 있습니다.
이때 진행 중인 쓰기를 버리거나 기본 저장을 중복 실행하면 안 됩니다.
확장을 끄면 다음 요청은 기본 저장을 사용합니다. 버전 미지원으로 복귀한 경우도 구분합니다.
네이티브 쓰기·일반 저장·종료 경합은 테스트 월드에서만 확인합니다.

## 결과를 남길 항목

문제가 생긴 시각, 확장 켜짐 여부, 실제 제공자/복귀 코드, 드래그/아이템 이동 상황,
카드의 게임 스레드 준비 시간과 전체 완료 시간을 남깁니다.
상세 저장 결과에는 다음 마이크로초 단위 진단값도 포함됩니다.

| 필드 | 의미 |
| --- | --- |
| `chunkCount` | 측정된 전용 청크 저장 호출 수 |
| `chunkBodyUs` | 청크 본문 점유 시간. 직렬화·원래 잠금 등을 포함하고 별도 측정한 쓰기 전달 시간은 제외 |
| `chunkHandoffUs` | 쓰기 전달·잠금 확보·동기 대체 쓰기에 사용한 게임 스레드 시간 |
| `animalSaveUs`, `collisionSaveUs` | 해당 저장 **호출**의 게임 스레드 점유 시간. 비동기 완료 전체 시간이 아님 |
| `otherCaptureUs` | 위 구간 외의 준비 시간 |

이 값들은 프레임 시간 통계나 FPS가 아닙니다. 새 게임 프로세스나 상시 로그 수집기를 만들지 않으며
현재 요청의 합계만 기록합니다. 큰 청크 직렬화·동물 저장·잠금·새 파일 생성 등으로 지연이 남을 수 있습니다.
실게임 인수 결과가 확인되기 전에는 `dev`/`main` 병합이나 일반 배포용 완성본으로 취급하지 않습니다.

## 게임 재시작 없는 호환 업데이트

API 9가 로드된 뒤에는 완료된 저장 사이에 호환되는 모듈을 교체할 수 있습니다.
새 앱을 다른 폴더에서 실행해도 같은 JVM의 연결부를 재사용합니다. 진행 중인 저장은
이전 코드로 끝나며, 다음 요청 결과의 moduleVersion/moduleSha256으로 적용본을 확인합니다.
모듈만 바뀌면 관측 연결을 유지하고, 브리지 실행부가 바뀌면 관측을 재연결합니다.
재연결 때 이전 예약 티켓은 무효화되며, 같은 캐릭터의 사망을 새 사건으로 만들면 실패입니다.
기본 저장이나 드래그 상태를 바꾸어 업데이트를 강행하지 않습니다.

## 0.11 프레임 분할 확인

카드는 누적 준비 시간이 아닌 **저장 작업의 최대 연속 게임 스레드 점유**를 표시합니다.
완료까지 걸리는 시간은 프레임 사이에 게임이 진행되므로 길어질 수 있습니다.
드래그 종료를 기다리거나 필수 차량 저장을 생략하지 않습니다.
같은 월드에서 최대 연속 점유와 체감 멈춤을 함께 비교하고, 아이템 이동과 미탑승 차량을 복원해 확인합니다.
4ms는 다음 청크로 넘어갈지 판단하는 예산이며 큰 단일 직렬화·메타데이터·잠금을 중간에 중단하는 보증이 아닙니다.
상세 로그의 captureMs는 누적 비용, maxCaptureSliceMs는 가장 긴 한 번의 점유입니다.

## 0.13.0 완료 시간 비교

앱을 다시 실행한 뒤 결과의 `moduleVersion=0.13.0`을 확인합니다. 이미 API 9가
연결된 게임은 재시작할 필요가 없습니다. 첫 준비와 반복 저장을 구분하여 같은
월드에서 전체 완료 시간과 최대 연속 점유를 함께 비교합니다.

고정 4청크 상한 대신 남은 4ms 예산을 쓰고 준비된 청크를 먼저 처리합니다.
가벼운 메타데이터 단계도 남은 예산 안에서 이어가지만, 최종 변경 검증과
플레이어·차량 캡처 사이에는 게임 루프를 끼워 넣지 않습니다.

`captureGapStatsV1`은 캡처 사이 간격, `captureYieldStatsV1`은 예산·파일 준비·
저장 준비 조건별 반환 횟수와 다음 호출까지 간격입니다. `completionStatsV1`은
완료 worker의 대기·commit·cleanup 시간을 구분합니다. `completionWaitUs`,
`dbAckUs`, `chunkIoStatsV1`, `nativeStatsV1`의 단위와 중첩 관계는
[저장 구조 문서](cooperative-save.md#diagnostics-and-acceptance)를 참조합니다.
프레임 사이 간격을 전부 디스크 대기로 해석하거나 중첩 지표를 합산하지 않습니다.

게임 내 `저장 완료`는 게임 저장의 완료이며 앱의 백업 파일 생성 완료와는 다릅니다.
게임 저장이 확인된 뒤에만 백업 수집을 시작합니다. USN을 사용할 수 없는 실행은
후속 `hash` 단계도 따로 비교해야 하며, 이 시간은 게임 저장 시간에 포함하지 않습니다.

0.13.0은 정규화된 경로별 순서를 지키는 두 파일 작업열을 사용합니다. 서로 다른
작업열의 파일만 병행하며 총 티켓·메모리 한도는 그대로입니다. 전역 준비 조건이
거짓일 때는 파일 기준 데이터만 미리 읽고, 공유 버퍼를 쓰는 청크 직렬화는 진행하지
않습니다. `readinessStageStatsV1`, `readinessReasonStatsV1`으로 대기 단계와 원인을,
`chunkIoDetailStatsV1`으로 파일 열기·해시·쓰기·마지막 검증 비용을 구분합니다.
두 작업열의 누적 처리 시간은 서로 겹치므로 전체 저장 시간과 단순 합산하지 않습니다.

디버깅 기록은 `%LOCALAPPDATA%/PzTools/config/app/default.toml`에서
`[logs].record_minimum_level = "Trace"`로 설정한 후 앱을 다시 실행합니다.
로그 화면의 경고 필터는 별개입니다. 성공은 `source.prepare.completed.detail`,
실패는 원본 `backup-worker`의 `run.failed.diagnostics`를 확인합니다. 준비 단계에서
보류된 자동 저장은 `run.cancelled`의 `code=source-deferred`와 `diagnostics`를 확인합니다.
시작 전 대기는 `bridgeAdmissionStatsV1`로 구분합니다. 보류·타임아웃의 진단은 그 시점까지의
부분 기록이며 저장 완료를 뜻하지 않습니다. 파일별·프레임별 로그를 무제한 생성하지 않습니다.
